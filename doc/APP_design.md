# 强化学习练习平台：Web 试用 + Electron 桌面端（Token 偶尔联网）授权设计说明

## 1. 背景与目标

你要做一个面向学习者的强化学习练习平台，练习形式是 **Python**。
由于 RL 训练需要算力，如果全部放在云端，会带来成本与滥用风险。因此采用：

* **Web：提供第一章/入门试用（极轻量、几秒完成）**
* **Electron：提供完整题库与本地训练（用户电脑承担算力）**
* **付费：一次性小额买断（如 $1），解锁所有练习**
* **授权：偶尔联网刷新 token，兼顾离线体验与可控性**

### 核心目标

* 低门槛体验：用户无需安装即可快速“跑通”第一章
* 成本可控：大部分训练不消耗你的服务器 CPU
* 可持续迭代：题库可更新、可分发新章节
* 授权够用：不追求军工级防破解，但能阻挡随手绕过与大规模滥用
* 良好体验：支持离线使用，只有“偶尔”需要联网验证

### 非目标（第一版不做）

* 强对抗反破解（反调试、反注入、底层加固）
* 强竞技排行榜（如需要公平排名，通常要云端隐藏评测重跑）
* 彻底防止题库被拷贝（现实做不到，只能提高门槛）

---

## 2. 产品结构与用户路径

### Web（免费试吃）

定位：**5 分钟内让用户感受到 RL 的“训练—收敛—策略改进”**
内容范围建议：

* 第一章：简单离散环境 + Q-learning（或 SARSA）
* 强可视化：Q 表热力图、策略箭头、reward 曲线
* 运行时间：1～5 秒为主（可强制超时）
* 目的：教育与转化，不承担“大训练”

> Web 尽量本地计算（浏览器内跑）或极轻量云端执行，以确保成本和风控简单。

### Electron（付费解锁后的主产品）

定位：完整的“RL 刷题 + 训练实验室”
内容范围：

* 全章节题库、讲解、参考实现（可选）
* 本地 Gymnasium 训练（分钟～半小时）
* 更丰富的算法（DQN/PPO 等）与可视化
* 本地缓存题目与资源，离线也能做题

### 付费与账号

* 用户付费后通过账号解锁全部内容
* 桌面端需要登录一次以激活，并且**偶尔联网刷新授权 token**

---

## 3. 为什么桌面端需要 token（以及“被破解”是什么）

桌面 App 的特点是：用户拥有本地程序文件。
如果“付费解锁”仅靠本地判断（例如一个布尔值或本地 license 文件），那么有心人可能通过：

* 修改本地配置/状态文件
* patch/替换 Electron 的前端逻辑
* Hook 授权判断函数

从而绕过付费。

因此采用的策略是：

> 把“解锁”从纯本地开关，升级为“服务端确认 + 短期 token + 离线宽限”。

这样即使有人绕过本地 UI，仍然拿不到你持续提供的在线价值（内容更新、章节下载、同步等），破解收益大幅降低。

---

## 4. 授权总体策略（高层）

### 4.1 核心原则

* **付费状态以服务端为准**：服务端记录用户是否已购买
* App 使用 **短期访问 token** 来证明“我已付费并被允许访问”
* token **会过期**：需要偶尔联网刷新
* 支持 **离线宽限**：过期后仍可离线使用一段时间，避免频繁联网打扰

### 4.2 离线宽限（建议）

* token 过期后，如果用户在一段时间内无法联网：

  * 仍允许访问本地已缓存的付费内容（宽限期，比如 30 天）
  * UI 明确提醒用户“需要联网验证”，但不立刻掐断学习
* 超过宽限期：

  * 付费内容入口锁定（免费内容仍可用）
  * 一旦联网验证成功，立即恢复

这套策略对买断小额产品很合适：体验好、又能防止“永久离线盗用”。

## 5. Web 与 Electron 的授权边界

### Web 端授权定位

Web 端主要是体验与引导，不应承担重度训练计算。
因此 Web 可以采用更轻的授权策略：

* **匿名可用**：第一章体验无需登录（降低门槛）
* **登录解锁增强体验**（可选）：例如保存进度、记录最佳成绩、同步到桌面端
* 付费与否在 Web 上也可展示（用于购买流程与账户中心）

### Electron 端授权定位

Electron 是付费后的主产品，需要更可靠的授权控制：

* 必须登录才能获取 token
* token 过期需要刷新（偶尔联网）
* 付费章节内容可通过“登录后下载”的形式获取与更新（比把全部题库打包进安装包更可控）

---

## 6. 内容分发策略（包含 Web 与 Electron）

### 6.1 Web 内容

Web 内容建议“固化且轻量”：

* 内置第一章题目与环境（或轻量从 CDN 加载）
* 尽量让计算在浏览器内完成（例如 Pyodide/简化环境/纯 JS 环境）
* 这样 Web 成本极低、体验稳定、无需担心云算力被滥用

### 6.2 Electron 内容

Electron 内容分为两类：

* **内置内容**：入门章节与示例（确保离线也能启动学习）
* **在线内容**：付费章节题目、讲解、更新包（登录后下载到本地缓存）

这种设计的好处：

* 你可以持续更新题库与修订题目
* 可以把“持续价值”绑定在线分发（破解本地开关也拿不到更新与新章）
* 用户体验仍然很好：下载后本地缓存，离线可用

### 6.3 “题库被拷走”怎么处理（高层）

题库内容被复制传播很难彻底防止。第一版建议采取“提高门槛”而非“死磕对抗”：

* 付费内容默认在线下载，而不是全部内置
* 可做轻量的内容完整性校验（防误改/损坏）
* 讲解/参考解等更“值钱”的部分可以更依赖在线分发与账号权限

---

## 7. 实现层面的安全边界（不深入接口）

### Electron 内部边界建议

* 授权 token 与敏感状态尽量由 Electron 主进程管理
* UI（渲染进程）通过受控方式请求“是否可访问/下载内容”等能力
* 这样能减少“前端一改就全解锁”的脆弱性（仍非绝对，但门槛更高）

### Web 与桌面端一致性

* Web 和 Electron 使用同一账户体系与付费状态
* 用户在 Web 付费后，桌面端下次联网刷新授权即可解锁，无需重新安装

---

## 8. 付费方案与价值绑定建议（结合你 $1 买断）

为了让“破解”即使发生也影响更小，建议把付费价值至少部分绑定在：

* 付费章节内容下载与更新
* 官方讲解/参考解（可选）
* 进度同步（可选）
* 未来新增章节（强烈建议：买断也能持续更新一段时间或长期）

如果你未来要做更强激励（如排行榜/证书）：

* 建议把“最终成绩”放到云端隐藏评测重跑（否则本地数据可伪造）

---

## 9. MVP 范围建议（第一版最小闭环）

### Web MVP

* 第一章：1～3 个超简单环境 + Q-learning
* 可视化（至少 reward 曲线 + 策略图）
* 运行限制（超时/步数上限）
* “下载桌面端”引导
* （可选）登录保存进度

### Electron MVP

* 登录 + token（偶尔联网刷新）
* 付费后解锁全部章节入口
* 付费内容可下载并本地缓存
* 本地 Python 训练运行与结果可视化
* 离线可用（含宽限期策略）

---

## 10. 取舍说明（给未来迭代留空间）

* 你不需要把精力花在极端对抗破解上：$1 买断更应追求“体验与传播”
* 关键是用设计把价值从“本地开关”迁移到“账号与持续内容/服务”
* Web 只做轻量体验，核心算力交给桌面端，成本和风险都可控
